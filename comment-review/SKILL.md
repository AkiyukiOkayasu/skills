# Comment Review

AI が書いたコメントは、モデルが見ていた試行錯誤の文脈を前提として書かれがちで、その文脈を共有していない読者には意味不明になる。また不要な詳細を含みがちでもある。このスキルは、コメントが「コードを読むだけでは分からないこと」だけを伝えるための基準を定め、レビューと記述の両方に使う。

## 使う場面

- コードコメントをレビューする（diff レビューの一部、またはコメントのみのレビュー）
- コードコメントを書く（予防）
- コメントの書き方について指摘する

## コメントの基準

コメントは「コードを読むだけでは分からないこと」だけを書く。コードを読めば分かることは書かない。

### 禁止

- 試行錯誤や経緯への言及（当初〜、以前は〜、いろいろ試した結果〜）
- 修正履歴の記述（バグを直した、追加した、などは git 履歴の仕事）
- コードの言い換え・再説明
- 数行にわたる詳細な背景説明（1行で言い切れない詳細は設計文書へ）
- 文の途中での改行（1コメントは1行で完結させ、次の行に続けない）

### 書くべきこと

- なぜ（why）：一見奇妙に見えるコードの理由
- 外部制約：実機事情、仕様、依存先の制約
- 非自明な契約・前提：呼び出し側が知るべき前提

### 目安

- 1行で言い切れるか。言い切れないなら、それは設計文書やコミットメッセージの内容
- 読者が「このコードを見て自然に気づくこと」は書かない
- 前提が共有されない人を読者として想定する

## 例

NG: 文の途中で改行しているコメント

```rust
// 分周によりノイズが広がる帯域を制限する。分周しないとノイズエネルギーが可聴帯域の
// 外まで拡散し、後段のLPF後に振幅が小さくなりすぎるため
div();
```

OK（行の途中で切らず、1行1文で完結させる）:

```rust
// 分周によりノイズが広がる帯域を制限する。
// 分周しないとノイズエネルギーが可聴帯域の外まで拡散し、後段のLPF後に振幅が小さくなりすぎるため。
div();
```

NG: 試行錯誤を共有前提にしたコメント

```rust
// 当初は SPI で読んでいたがノイズで不安定だったため、
// いろいろ試した結果 I2C に切り替えた
let data = read_i2c();
```

OK:

```rust
// 読み取りは I2C に限定（SPI はノイズで不安定なため）
let data = read_i2c();
```

NG: コードの言い換え

```rust
// データの長さを2バイトで表す
let len = (data.len() as u16) << 8;
```

OK（意味が非自明なら）:

```rust
// length は big-endian で格納される
let len = (data.len() as u16) << 8;
```

NG: 修正履歴

```rust
// バグ修正: タイマーをリセットする
reset_timer();
```

OK:

```rust
// 前回の計測値を破棄して再計測する
reset_timer();
```

## レビューの進め方

1. 対象をコメント行だけに絞る。コードロジックのレビューはこのスキルの対象外。
2. 各コメントを次の3段階で判定する:
   - OK
   - 修正: 意図は伝わるが書き方の問題。1行の修正案を添える
   - 削除: コメント自体が不要（コードの言い換え、経緯、試行錯誤）
3. 理由は「どの基準に反するか」で示し、具体例を使って指摘する
4. コメントの有無だけでなく、追加が必要な場所（非自明な why が書かれていない）も指摘する

## レビュー時の運用

- 判定はシンプルなルールなので、小さなモデルのサブエージェントでも十分対応できる。まずは small_model のサブエージェントにレビューさせる
- 曖昧な判定が続く場合のみ、より強いモデルに上げる
- 修正作業はメインエージェントが行い、サブエージェントは読み取り専用の指摘まで

## アンチパターン

- チーム内の暗黙知を前提にした言い回し（「例のあの件」「あの調査で分かったように」）
- 「〜する必要がある」と書くだけの結論コメント（なぜが必要かが無い）
- 自明なコードに実況を書くコメント
