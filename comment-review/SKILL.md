# Comment Review

AI が書いたコメントは、モデルが見ていた試行錯誤の文脈を前提としがちで、その文脈を共有しない読者には意味不明になる。コメントは「コードを読むだけでは分からないこと」だけを書く。

## 基準

### 禁止

- 試行錯誤や経緯への言及（当初〜、以前は〜、いろいろ試した結果〜）
- 修正履歴（バグを直した、追加した。git 履歴の仕事）
- コードの言い換え・再説明
- 数行にわたる背景説明（1文で言い切れない詳細は設計文書へ）
- 文の途中での改行。1文は必ず1行で書く。行末が読点や助詞（`の` `で` `し` `が` `を` `に` `は` `と` `も` `ため` `ので` `から` `まで` `より`）で終わる行は、文が途中で切れている。複数文は文ごとに改行してよい。コメントには行長制限（80/100/120桁）を適用しない。

### 書くべきこと

- なぜ（why）：一見奇妙に見えるコードの理由
- 外部制約：実機事情、仕様、依存先の制約
- 非自明な契約・前提：呼び出し側が知るべき前提

### 目安

- 1文で言い切れないなら、それは設計文書やコミットメッセージの内容
- 1文が長い場合は、文を短くするか句点で文を分ける。途中で折り返さない
- 読者が「このコードを見て自然に気づくこと」は書かない
- 前提が共有されない人を読者として想定する

### 改行の自己チェック

コードを書き終えたら、追加・変更したコメント行を上から走査する。

- 行末が `、` や助詞（`の` `で` `し` `が` `を` `に` `は` `と` `も` `ため` `ので` `から` `まで` `より`）で終わっていないか
- 文が続いているのに次の行へ折り返していないか
- 該当したら、次の行と結合して1文1行にする

スキルは必要時にしか読み込まれない。常時適用したいルールは `~/.config/opencode/AGENTS.md` にも置く。

## 例

NG: 文の途中で改行しているコメント

```rust
// 分周によりノイズが広がる帯域を制限する。分周しないとノイズエネルギーが可聴帯域の
// 外まで拡散し、後段のLPF後に振幅が小さくなりすぎるため
div();
```

OK（行の途中で切らず、1行1文で完結させる）:

```rust
// 分周によりノイズが広がる帯域を制限する。
// 分周しないとノイズエネルギーが可聴帯域の外まで拡散し、後段のLPF後に振幅が小さくなりすぎるため。
div();
```

NG: 試行錯誤を共有前提にしたコメント

```rust
// 当初は SPI で読んでいたがノイズで不安定だったため、
// いろいろ試した結果 I2C に切り替えた
let data = read_i2c();
```

OK:

```rust
// 読み取りは I2C に限定（SPI はノイズで不安定なため）
let data = read_i2c();
```

NG: コードの言い換え

```rust
// データの長さを2バイトで表す
let len = (data.len() as u16) << 8;
```

OK（意味が非自明なら）:

```rust
// length は big-endian で格納される
let len = (data.len() as u16) << 8;
```

NG: 修正履歴

```rust
// バグ修正: タイマーをリセットする
reset_timer();
```

OK:

```rust
// 前回の計測値を破棄して再計測する
reset_timer();
```

## レビューの進め方

1. 対象をコメント行だけに絞る（コードロジックのレビューは対象外）
2. 各コメントを OK / 修正 / 削除 で判定する。修正は1行の修正案を添える
3. 理由はどの基準に反するかで示す
4. 非自明な why が書かれていない箇所（追加すべきコメント）も指摘する

## アンチパターン

- チーム内の暗黙知を前提にした言い回し（「例のあの件」「あの調査で分かったように」）
- 「〜する必要がある」と書くだけの結論コメント（なぜが必要かが無い）
- 自明なコードに実況を書くコメント
