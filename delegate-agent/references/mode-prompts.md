## 共通原則

DeepSeek V4 Flashは、高速・低コストな外部エージェントとして、探索、明確なPlanの実装、文書化、commit準備、独立レビューに使い分ける。

Codexは親エージェントであり、委譲判断、結果の採否、元コードでの再確認、テスト、統合、最終品質保証を担当する。外部エージェントの回答だけで作業完了とはみなさない。

## explore

ファイルを変更させず、コードベース全体を読むための索引を作る。特に次を依頼する。

- プロジェクト全体の目的
- 主要なディレクトリ
- エントリーポイント
- 主要モジュールの責務
- データフロー
- 状態管理
- テスト構成
- 今回の作業に関連するファイル
- 最初に読むべきファイル
- 不明点・未確認事項

依頼には次を含める。

```text
このリポジトリを変更せずに調査してください。
確認できた事実と推測を分けて報告してください。
各項目に相対pathと根拠を付けてください。
```

結果はコードベースを読むための索引・仮説として扱う。重要な仕様、構造、path、API、呼び出し関係はCodexが元コードで再確認し、存在しないファイルやAPI、推測の事実化を除外する。

## review

ファイルを変更させず、細かなミスだけでなく実装の方向性を疑う独立レビューを行う。DeepSeekでは次を重視する。

- 実装方針そのものが目的に合っているか
- 誤った前提に基づいていないか
- 問題設定を誤解していないか
- 既存アーキテクチャと整合しているか
- 責務分割や抽象化が妥当か
- 不要に複雑になっていないか
- より単純で堅牢な代替案がないか
- 局所的には正しくても全体では問題がないか

通常の「バグを探して」だけでは局所レビューに寄るため、設計前提を疑うことを明示する。結果は次の順で分ける。

1. 方針または設計上の問題
2. 具体的な実装上の問題
3. 未確認の前提または質問
4. 問題がないと判断した点

Sol/Codex側のレビューとは非対称にする。Sol/Codexはoff-by-one、条件分岐、error処理、API誤用、型・bit幅、競合・状態遷移、テスト不足など局所的な正しさを確認し、DeepSeekは方針・前提・全体整合性を確認する。DeepSeekの指摘もCodexが元コードと仕様で再検証する。

## work

判断の余地が少なく、承認済みPlanに従う明確な小規模作業だけを行う。依頼には対象、決定済み方針、完了条件、禁止事項を明記する。

```text
承認済みPlanの次の項目だけを実施してください。

対象:
- src/example.rs
- tests/example.rs

決定済みの方針:
- 公開APIは変更しない
- 既存のFoo実装と同じ構成を使う

完了条件:
- 指定機能が実装されている
- 必要なテストが追加され、指定テストが成功する

禁止事項:
- 無関係なリファクタリング
- 指定範囲外の変更
- 新しい抽象化の導入
- 公開APIの変更
- commit、push

最後に変更ファイル、実装内容、実行テスト、未解決事項を報告してください。
```

実装とcommitは分離する。Codexがdiff、対象外変更、Plan遵守、テストを確認してから、必要なら別途commit工程へ進む。文書化も、対象と既存形式が明確ならworkで扱える。

## commit

変更内容が完成し、Codexがdiffとテストを確認した後だけ使う。commit対象pathを明示し、対象外ファイルを絶対に含めない。

```text
現在の作業ツリーから、今回のタスクに関係する変更だけをコミットしてください。

コミット対象:
- src/example.rs
- tests/example.rs

実施内容:
1. git statusを確認する
2. 対象ファイルの差分を確認する
3. 必要なテスト結果を確認する
4. 指定ファイルだけを明示的にstageする
5. 内容に合うcommit messageでcommitする
6. commit結果を報告する

禁止事項:
- git add -A
- git add .
- git commit -am
- 対象外ファイルのstage
- 既存変更の破棄
- reset、rebase、amend、push
```

作業ツリーに変更が混在する場合は、ファイル指定または部分stageで切り分ける。切り分けに判断が必要ならCodexが行う。commitは実装とは別工程であり、runnerが明示的な許可と対象pathを強制できる場合だけ実行可能とする。現状runnerの実装モードは`commit-prep`までで、直接commitは未実装である。

## 出力契約

委譲結果には、少なくとも次を含める。

- 実行したモード
- 使用したモデル
- 終了状態
- 外部エージェントの出力
- ファイル変更の有無と変更path
- Codexが確認すべき事項

成功・失敗、未完了、timeout、禁止tool、対象外変更を曖昧にしない。失敗時は理由を返し、成功したように扱わない。

## Codex側の検証

### explore

- 重要な構造を元コードで確認する
- 存在しないファイルやAPIがないか確認する
- 推測を事実として扱わない

### review

- 各指摘を元コードと仕様で確認する
- 誤検出や前提違いを除外する
- GPT/Sol側の細部レビューとの重複を整理する
- 最終的な重要度をCodexが決める

### work

- `git diff`を確認する
- 対象外の変更がないか確認する
- 実装が決定済み方針に従っているか確認する
- 必要なテストを再実行または確認する

### commit

- commit hashを確認する
- `git show --stat --oneline <hash>`を確認する
- 必要なら`git show <hash>`で内容を確認する
- 自動的にpushしない

## 失敗条件

次の場合は委譲失敗として扱う。

- executableが存在しない、認証されていない、または指定モデルが利用できない
- 非ゼロ終了、空出力、malformed output、必要な終了イベントの欠落
- read-only modeでファイルを変更した
- 対象外pathを変更した
- 必要なテストが失敗した
- 親作業ツリーが予期せず変更された
- commit対象に無関係な変更が混在した
- commitが作成されていない
- 外部エージェントの結果だけでは作業完了を確認できない

委譲失敗時、Codexが継続可能ならその後の作業はCodex自身が行う。
